# hiui-design v2 架构总览

## 1. 文档目标

本文件用于统一 `hiui-design` 在主文档层的正式口径，解决三个长期混用的问题：

- 项目如何接入，与单页如何生成，经常被写在同一层。
- 页面输入来源、页面类型判断、页面生成方式，经常被混写成一条分类链。
- 当标准典型页面模板不能完整覆盖需求时，系统缺少统一说法，容易在“补一个新页型”和“临场手写 patch”之间摇摆。

`hiui-design v2` 的目标不是再增加一批页面模板，而是把现有能力整理成一条设计、生成、验收都能共用的稳定链路。

## 2. 适用范围

本方案当前覆盖以下范围：

- `hiui-design` 在项目中的接入方式说明。
- 页面输入来源的统一归一化。
- 页面类型的正式判断口径。
- 标准模板不足时，基于基础模板做局部改造的生成路径。
- 完全非典型页面的 AI 前置引导、最小 contract 与样本验证口径。
- 完全非典型页面 v1 首版支持范围冻结、family workflow planning artifacts 与执行演进方案。
- 与上述能力对应的 brief、生成与校验原则。

本方案当前不覆盖以下内容：

- 非典型页面已对外开放并可承诺完整 family-specific generator 主链路。
- 将所有真实诉求预先枚举成固定“增强类型列表”。
- 将单次业务特例直接注册为正式页面类型。
- 脱离 HiUI5 与 `local-managed-runtime` 设计约束的自由页面生成。

## 3. 架构总口径

`hiui-design v2` 建议固定为“两层一链路”的表述方式。

### 3.1 项目级

项目级只回答一个问题：`hiui-design` 以什么方式接入当前项目。

这一层当前只保留 `接入模式`：

- `host-integration`
- `rules-only`

接入模式是项目 onboarding 阶段的一次性决策。进入单页评审、单页生成和单页验收时，默认继承该上下文，不再把它当成每次页面讨论都要重新判断的变量。

### 3.2 页面级主链路

页面级统一使用以下主链路：

`信息输入方式 -> 页面家族 / 页面类型 -> 生成路径`

三者分别回答不同问题：

- `信息输入方式`：AI 根据什么材料理解页面。
- `页面家族 / 页面类型`：这页属于哪一类页面体系，以及命中的主骨架类型。
- `生成路径`：在当前页面类型下，应该采用哪种落地方式。

这里需要明确一点：

- `典型页面变体` 不是页面级主链路中的一个独立分类层。
- 在主文档口径中，`典型页面变体` 指的是“典型页面命中基础模板上的局部改造这条生成路径”。
- 换言之，它是一种生成方式说明，不是一层新的页面分类体系。

### 3.3 三类生成路径

页面生成默认只落在以下三类路径中：

- `标准模板直出`
- `基础模板上的局部改造`
- `独立工作流生成`

它们不是三种新的页面类型，而是三种不同的页面落地方式。

对应关系如下：

- 当标准典型页面模板已足够覆盖需求时，走 `标准模板直出`。
- 当页面仍然明显属于某个典型页面类型，但标准模板不能完整覆盖用户诉求时，走 `基础模板上的局部改造`。
- 当页面本身已经有独立工作流，例如 `data-visualization`，走 `独立工作流生成`。

其中，`基础模板上的局部改造` 是典型页面体系的通用生成路径，不预先限定只能由某几个基础页型使用。任一典型页型只要满足“基础页型明确、主骨架仍保留、差异可约束为局部改造”这三个条件，都可以进入该路径。

## 4. 核心概念定义

### 4.1 接入模式

接入模式是项目级前置事实。它说明 `hiui-design` 如何进入当前项目，影响 preview、doctor、宿主联调与规则落地边界，但不直接决定单个页面属于什么页面类型。

### 4.2 信息输入方式

信息输入方式是页面理解来源，不是页面结果。

当前统一支持以下输入方式：

- `页面提示词`
- `原型截图`
- `旧系统重构`

后续若增加新输入方式，也应继续放在这一层，而不是混入页面类型或生成路径。

`原型截图` 的 P0 正式口径已经固定为：

- 单张主页面截图
- AI 在对话中完成截图理解
- AI 在对话中完成页型推荐与提示词草稿
- 用户在对话中确认最终页型与最终提示词
- 确认结果以 `chat-confirmed + in-memory handoff` 的方式进入 brief / generate 主链路

P0 明确不引入：

- 多图输入
- 独立 JSON artifact
- 仓库内确认 UI
- 本地 image-to-code 脚本

### 4.3 页面类型

页面类型定义页面的主骨架，是结构层判断，不是业务命名。

当前主页面类型包括：

- `典型页面`
- `数据可视化页面`

其中，`典型页面` 在实现层继续落到正式页型，例如普通表格、数据统计表、树形表格、左树右表、抽屉表单、抽屉详情、全页编辑、全页详情等。这些是典型页面内部的正式基础页型，不等于“典型页面变体”。

### 4.4 生成路径

生成路径定义的是“在页型已明确之后，页面应如何落地”。

这意味着：

- 页面类型先于生成路径。
- 生成路径依附于页面类型存在。
- 同一个页面类型可以对应不同生成路径。

例如：

- 某个普通表格页可能直接走 `标准模板直出`。
- 另一个仍然属于普通表格页的需求，可能因为多了一层用户明确要求的局部结构，而改走 `基础模板上的局部改造`。

### 4.5 典型页面变体

在 v2 主文档中，`典型页面变体` 的正式定义如下：

> 典型页面变体，是典型页面在标准模板不足时，基于明确基础页型进行受控局部改造的一类生成场景。

因此：

- 它不是新的页面类型。
- 它不是一张可穷举的增强类型表。
- 它不是“把典型页手写得更复杂一点”。
- 它表示页面仍然保留基础典型页的大多数特征，但标准模板需要针对本次诉求做局部调整。

### 4.6 pageAdjustmentContract

`pageAdjustmentContract` 是执行层的正式建模载体，用于描述“本次页面需求相对基础模板要做什么局部改造”。

它的职责不是给系统提供一份预设的扩展类型清单，而是把当前需求抽取成一份可执行、可校验、可回溯的局部改造说明。

在当前实现中，需要再明确一层执行口径：

- `pageAdjustmentContract` 不再只停留在 brief 或报告层。
- 当 contract 命中生成器已接通的受控区域锚点时，系统会在保留基础模板主骨架的前提下，自动把局部改造插入到对应结构位置。
- 当 contract 没有命中稳定锚点时，系统必须停止，而不是退回到自由手写页面。

### 4.7 non-typical-page v1 支持边界

`non-typical-page` 在 v2 中仍然不是模板页型，而是 family 级 rules-composition 工作流。

它的第一事实层不是 archetype，而是共享设计指导：统一 `PageHeader`、统一 `whiteBody`、单一主阅读流、统一字体/颜色/间距、统一组件语义，以及图表也必须继续服从 `hiui-design` 规范。

当前已冻结的 v1 支持边界如下：

- 输入方式对外支持 `page-prompt`、`prototype-screenshot` 与 `figma-design-restore`
- 项目模式只支持 `host-integration` 与 `rules-only`
- 页面场景只支持新页面生成
- machine term `archetype` 只支持 `process-stage-sync` 与 `selection-detail-sync`

设计还原补充口径：

- `figma-design-restore` 与 `design-screenshot-restore` 属于独立的 `design-restore` 输入链，不再复用 `prototype-screenshot` 的原型生成口径
- 当前第一阶段只对外开放 `figma-design-restore`；`design-screenshot-restore` 保留为第二阶段降级入口
- 它们当前已经完成主链脚本接线，但正式执行前仍要求上游先提供 `confirmedDesignRestoreInput`
- 当 `confirmedDesignRestoreInput.restoreDecisionPackage` 已经能形成单一路由结论时，`generation-brief`、`plan-page-task`、`generate-page-from-brief` 与 `integration-preflight` 可自动补齐缺失的 `page-type` / `page-family`
- 设计还原结果必须继续落在 HiUI5 与 `local-managed-runtime` 约束内，不允许退回自由页面生成

当前仍然不支持：

- `legacy-system-reconstruction`
- 未经样本验证的新协调模式
- 第三方复杂画布 / 图引擎页面

当前状态补充：

- family-specific generator 已在仓库内部接线
- validated v1 scope 已由 `page-family-workflows.manifest.json` 对外声明 `generatorReady=true`
- design-restore 已补首轮样本回归留痕，见 `docs/generation/design-restore-sample-batch-round-1.md`
- 因此当前准确口径是“validated v1 scope 对外正式开放可用”，不是“无限制全量开放可用”

这里的 `archetype` 只是执行层 machine contract 的内部协调模式词汇，不表示页面模板枚举，也不意味着截图样本可以直接沉淀成新页型。

这一层口径的作用，是先冻结首版执行范围，避免在 generator 尚未接通前持续扩大页面家族边界或放大视觉逃逸。

## 5. 页面级统一流程

### 5.1 输入归一化

首先接收输入材料，并统一整理成结构化页面描述。

这一阶段只回答“用户提供了什么证据”和“页面看起来要完成什么任务”，不直接下结论生成什么代码。

当输入方式为 `原型截图` 时，输入归一化后还必须先形成：

- `pageTypeRecommendation`
- `promptDraft`
- `unknowns`

并在继续进入页型判断前，先在 AI 对话中完成：

- `confirmedPageType`
- `finalPrompt`

### 5.2 页面类型判断

在输入归一化之后，先判断页面主骨架属于哪一种页面类型，并命中对应的正式基础页型。

这里必须优先依赖现有事实源，例如：

- `page-type-map.md`
- `page-types.manifest.json`
- 官方母版

如果基础页型尚未明确，不允许继续讨论局部改造。

### 5.3 生成路径判断

页面类型明确后，再判断应该走哪条生成路径：

- 标准模板已经覆盖，走 `标准模板直出`
- 基础页型明确且大多数特征保留，但标准模板不足，走 `基础模板上的局部改造`
- 页面类型本身已有独立工作流，走 `独立工作流生成`

这里的判断顺序不能颠倒。系统不应先讨论“是不是变体”，再倒推基础页型。

### 5.4 brief 形成

brief 至少需要固定以下事实：

- 输入方式
- 若命中 `原型截图`：推荐页型、提示词草稿摘要、确认方式、确认页型、最终提示词摘要
- 页面类型与基础页型
- 生成路径
- 官方母版起点
- 结构保留要求
- 局部改造说明（如命中）
- 设计系统约束
- 校验要求

其中：

- 若走 `标准模板直出`，brief 重点是标准业务槽位替换。
- 若走 `基础模板上的局部改造`，brief 必须补齐 `pageAdjustmentContract`。

### 5.5 执行生成

生成时必须遵守以下统一原则：

- 永远先从已命中的官方基础模板起步。
- 典型页面变体场景不允许回退到空白文件手写一个“类似典型页”的页面。
- 局部改造部分继续优先使用 HiUI5 与 `local-managed-runtime` 的组件与 token。
- 局部改造只能发生在本次 contract 说明的受控区域内，不能反向推翻主骨架。
- 对已接通的受控区域，生成器应自动完成局部改造执行；对未接通的区域，必须显式停止，不允许用“模板外观 + 自由补丁”的方式绕过边界。

### 5.6 分层校验

校验统一拆成两层：

- `主类型校验`
- `局部改造 contract 校验`

优先级固定为：

- 主类型规则优先。
- 局部改造 contract 只能补足模板覆盖，不能覆盖主类型边界。

## 6. 典型页面变体的正式边界

### 6.1 什么情况属于典型页面变体

一个页面诉求满足以下条件时，可以认为它属于典型页面变体场景：

- 基础页型明确。
- 页面仍然保留基础页型的大多数结构特征和主要阅读流。
- 差异并非只停留在标题、按钮、字段或文案层。
- 标准模板不能完整覆盖用户诉求，但差异仍可约束为局部改造。
- 改造后页面仍然明显归属于原基础页型。

### 6.2 什么情况不属于典型页面变体

以下情况不应纳入典型页面变体：

- 只是标准模板的业务内容替换。
- 只是增加零散提示、公告、按钮或文案。
- 页面主骨架已经明显不再属于原基础页型。
- 需要重写主壳层、owner 关系、主滚动链或主要阅读流。
- 需要通过枚举一个新“增强类型名”来证明它成立。

### 6.3 典型页面变体的核心约束

典型页面变体必须同时满足以下硬约束：

- 基于基础模板生成，而不是脱离模板另起一页。
- 调整的是局部结构，不是整页重写。
- 调整部分仍然受 HiUI5 与 `hiui-design` 设计基线约束。
- 调整后的页面仍然可以用“这是哪个基础页型”清楚回答。

## 7. 执行层建模口径

执行层的核心不是“预设有多少种增强类型”，而是“如何把当前需求建模成相对基础模板的局部改造”。

v2 建议固定以下建模原则：

### 7.1 先有基础页型，再有局部改造

所有局部改造描述都必须依附于明确的基础页型，不能脱离基础页型单独存在。

### 7.2 描述的是本次需求，不是全量枚举表

`pageAdjustmentContract` 描述的是“当前页面相对基础模板需要做什么调整”，不是“该页型长期允许哪些增强类型”。

这意味着：

- `allowedRegions` 等字段可以继续存在。
- 但这些字段描述的是本次需求中的受控改造位置，不代表产品层已经预设了一张固定扩展区域字典。

### 7.3 建模的重点是保留与调整的关系

执行层需要同时说清楚两件事：

- 哪些基础页型特征必须保留。
- 哪些局部结构需要按用户诉求调整。

如果只能说清“要加什么”，却说不清“什么不能动”，说明建模仍不完整。

### 7.4 不以示例代替能力定义

`table-basic + tabs` 之类案例可以作为说明样例，但不能上升为“典型页面变体能力的定义方式”。能力定义应落在原则、边界与 contract 结构上，而不是落在某几个示例组合上。

## 8. 风险与边界

### 8.1 主要风险

当前方案的主要风险包括：

- 如果主文档继续把“典型页面变体”当成分类层，会造成页面类型与生成路径混用。
- 如果执行层把 `allowedRegions` 等字段解释成固定枚举表，会重新走回“先定义增强类型”的旧路径。
- 如果局部改造边界定义过宽，生成器会退化成“带模板外观的自由手写页”。
- 如果只强调用户诉求，不强调基础页型保留要求，验收阶段无法判断页面是否仍然属于典型页面。

### 8.2 控制原则

为避免上述风险，v2 建议长期保持以下控制原则：

- 主文档始终使用 `信息输入方式 -> 页面家族 / 页面类型 -> 生成路径` 作为页面级主链路。
- `典型页面变体` 只作为“基础模板上的局部改造”这条路径的业务口径，不单独升级为页面分类层。
- 执行层继续使用 `pageAdjustmentContract`，但只描述本次需求相对基础模板的局部改造关系。
- 所有局部改造都必须接受“仍然属于原基础页型”的校验。

## 9. 演进建议

v2 的近期演进建议如下：

- 先稳定主文档口径，避免项目级、页面级、执行级概念继续混写。
- 再稳定 `pageAdjustmentContract` 的执行层描述，使其从“示例化字段集合”变成“正式建模载体”。
- 继续在统一归一化链路下扩充原型截图、旧系统重构等输入方式，但不打破当前 `chat-confirmed + in-memory handoff` 的 P0 口径。
- 对 `non-typical-page`，先冻结首版支持范围并补 family workflow manifest、family execution brief 与 family-specific generator，再决定是否开放更大范围。
- 最后再基于真实案例验证哪些诉求适合继续沉淀为稳定规则，哪些诉求仍应留在一次性局部改造层。

## 10. 结论

`hiui-design v2` 的正式口径应固定为：

- 项目级只讨论 `接入模式`。
- 页面级只讨论 `信息输入方式 -> 页面家族 / 页面类型 -> 生成路径`。
- `典型页面变体` 不是新的页面分类，而是典型页面在标准模板不足时，进入“基础模板上的局部改造”这条生成路径的正式说法。
- 执行层不做增强类型枚举，而是把当前需求建模成一份相对基础模板的 `pageAdjustmentContract`。
- `non-typical-page` 首版只在已冻结范围内推进 family-specific execution support，未接通前不得夸大为“已具备完整自动生成能力”。

只有这四层关系同时成立，设计语言、生成语言和验收语言才不会继续分叉。
