# HiUI5 典型页面变体与局部改造建模规范

## 1. 文档定位

本文件不是页面类型清单，也不是页面增强类型字典。本文件只解决一件事：

> 当某个页面已经明确属于典型页面体系中的某个基础页型，但标准模板无法完整覆盖用户诉求时，执行层应该如何把这次需求建模成“基于基础模板的局部改造”。

为避免与主文档口径冲突，本文件固定使用以下前提：

- `典型页面变体` 是业务和方案层的说法。
- 执行层真正落地的对象是 `pageAdjustmentContract`。
- `pageAdjustmentContract` 描述的是“当前需求相对基础模板的局部改造关系”，不是一张预设增强类型表。
- 在执行层，稳定的能力名是 `local-adjustment`；`典型页面变体` 只是其中面向典型页业务场景的命名。

## 2. 与主文档的关系

主文档中的页面级主链路是：

`信息输入方式 -> 页面家族 / 页面类型 -> 生成路径`

本文件只覆盖其中一条生成路径：

- `基础模板上的局部改造`

因此，本文件有三个边界：

- 不重新定义项目接入模式。
- 不重新定义页面类型。
- 不把“典型页面变体”提升为页面分类层。
- 不把“局部改造”误收窄为 `typical-page` 私有能力。

本文件只回答以下问题：

- 什么样的需求可以进入“基础模板上的局部改造”。
- 什么样的需求不应进入这条路径。
- 进入后，执行层应该如何建模、生成和校验。

## 3. 正式定义

### 3.1 典型页面变体是什么

`典型页面变体` 指的是这样一类生成场景：

- 页面已经命中一个明确的基础典型页型。
- 基础 family 已经明确，且仍然由当前 family 主结构承担主任务。
- 页面仍然保留该基础页型的大多数特征。
- 用户诉求超出了标准模板当前直接覆盖的范围。
- 这部分差异可以被约束为一次受控的局部改造。

在执行层，这类场景统一表现为：

- 从基础页型官方模板起步。
- 通过 `pageAdjustmentContract` 描述本次局部改造。
- 在受控区域内完成生成。
- 先通过基础页型校验，再通过局部改造校验。

### 3.2 典型页面变体不是什么

以下内容不属于典型页面变体：

- 单纯的业务槽位替换。
- 只改标题、字段、按钮、文案、表格列。
- 临时加一个说明块、提示条、状态文案。
- 需要脱离基础模板重新手写页面。
- 需要改写主壳层、主滚动链、header owner、whiteBody owner、分页 owner。
- 需要先发明一个新“增强类型名”，才能说明这页为什么成立。

### 3.3 执行层的正式落点

`典型页面变体` 在执行层的正式落点不是“变体类型”，而是 `pageAdjustmentContract`。

补充约束：

- 当业务口径仍然是“典型页面变体”时，执行层仍然使用 `pageAdjustmentContract`。
- 当页面属于 `analytics-page`，但 family 主结构仍然稳定、差异可被描述为受控改造时，执行层仍可进入同一条 `local-adjustment` 路径；只是业务口径不再把它叫做“典型页面变体”。

因此，执行层不要求先回答“这属于哪种增强类型”，而要求回答：

- 基础页型是什么。
- 哪些典型页特征必须继续保留。
- 用户到底要求局部改哪里。
- 这些调整相对基础模板如何插入或重组。
- 哪些结构不能碰。
- 调整后如何继续满足 HiUI5 与 `hiui-design` 约束。

## 4. 进入与退出条件

### 4.1 可以进入局部改造路径的条件

一个诉求只有在同时满足以下条件时，才应进入典型页面变体链路：

- 基础页型已经明确。
- 页面仍然保留基础页型的大多数结构特征和主要阅读流。
- 差异不只是业务内容层，而是对局部结构组织有真实影响。
- 差异可以被约束在一组可描述、可校验的受控调整中。
- 调整后页面仍然可以明确回答“这页属于哪个基础页型”。

这条路径适用于任一典型页面基础页型，不预设只有表格类页型才会出现局部改造。

### 4.2 不应进入局部改造路径的条件

出现以下任一情况时，原则上不应继续按典型页面变体处理：

- 基础页型本身尚未判断清楚。
- 差异只停留在文案、字段、按钮或数据内容层。
- 差异要求自由重组整页主体，而不是局部调整。
- 差异要求改写主壳层、主滚动链或关键 owner 关系。
- 差异已经明显更接近新的页面类型或独立工作流。
- 差异无法沉淀成机器可读 contract，只能靠人工口头解释。

### 4.3 退出条件

即使一个诉求最初看起来像典型页面变体，只要在建模过程中出现以下情况，也应立即退出该路径：

- 无法说清哪些基础页型特征必须保留。
- 无法说清局部改造到底作用于哪一段结构。
- 无法说清哪些结构严禁改动。
- 无法证明调整后页面仍然明显属于原基础页型。

退出后应回到上层重新判断：

- 是不是其实仍然属于标准模板直出。
- 是不是已经超出典型页面边界，需要新的页面类型或独立工作流。

## 5. 执行层建模原则

### 5.1 先有基础模板，后有局部改造

局部改造永远依附于基础模板存在。执行层不允许跳过基础模板，直接把“像典型页一样的页面”当作合法结果。

### 5.2 不做增强类型枚举

执行层不预设“tabs 增强”“双层筛选增强”“摘要增强”之类固定类型列表。

原因很明确：

- 如果某种结构差异已经足够稳定、足够可复用，并且可以标准化进模板，那它应优先回到正式基础页型能力中处理。
- 进入局部改造路径的，恰恰是当前无法被标准模板直接穷举覆盖、但又没有脱离基础页型的那部分真实诉求。

因此，建模对象必须是“当前需求相对基础模板的改造关系”，而不是“系统预设好的增强类型名”。

### 5.3 重点描述保留关系与调整关系

一个可执行的局部改造建模，至少要同时覆盖两类信息：

- `保留关系`
  说明哪些基础页型特征必须保持不变。
- `调整关系`
  说明哪些局部结构需要按当前用户诉求新增、插入、替换或重组。

只写“要加什么”而不写“什么不能动”，不属于完整建模。

### 5.4 字段是描述容器，不是预设字典

执行层可以继续使用如下字段：

- `retainedTypicalCharacteristics`
- `userAdjustmentIntent`
- `structureSummary`
- `intentContract`
- `allowedRegions`
- `forbiddenRegions`
- `insertPositionRule`
- `designSystemConstraints`
- `layoutPreservationRule`
- `adjustmentValidationRules`

但这些字段的语义必须统一解释为：

- 它们描述的是“当前页面相对基础模板的局部改造事实”。
- 它们不是“某个页型固定允许扩展哪里”的全局枚举字典。
- 它们可以出现页面级相对位置描述，而不要求都映射成预设 slot 名称。
- `structureSummary` 负责说明稳定主区域、区域职责、阅读流和交互归属。
- `intentContract` 负责说明 `mustHave` 与 `mustNotAdd` 的结构事实。

### 5.5 示例只能用于说明，不用于定义能力

`table-basic + tabs` 可以作为示例帮助理解“局部改造”是什么，但不能演变为能力模型本身。

能力模型必须稳定在以下层面：

- 是否保留基础页型
- 是否属于局部改造
- 如何生成
- 如何校验

而不是稳定在某几个示例组合上。

## 6. pageAdjustmentContract 建模口径

### 6.1 contract 的职责

`pageAdjustmentContract` 的职责是把一次用户真实诉求转成执行层可消费的局部改造说明。

它至少要固定以下事实：

- `basePageType`
- `retainedTypicalCharacteristics`
- `userAdjustmentIntent`
- `allowedRegions`
- `forbiddenRegions`
- `insertPositionRule`
- `designSystemConstraints`
- `layoutPreservationRule`
- `adjustmentValidationRules`

### 6.2 字段解释

- `basePageType`
  说明本次局部改造依附于哪个正式基础页型。

- `retainedTypicalCharacteristics`
  说明哪些典型页核心特征必须继续保留。这是“页面仍属于原基础页型”的直接证据。

- `userAdjustmentIntent`
  用工程可执行的话描述本次用户到底要求局部改什么。

- `allowedRegions`
  描述本次需求允许发生改造的相对结构区域。它描述当前页面事实，不代表预设扩展字典。

- `forbiddenRegions`
  描述本次需求中严禁改动的结构或 owner。

- `insertPositionRule`
  描述局部改造相对基础模板应如何插入、挂靠或排序。

- `designSystemConstraints`
  说明改造部分如何继续遵守 HiUI5、`local-managed-runtime` 与 `hiui-design` 的组件和 token 规则。

- `layoutPreservationRule`
  说明哪些布局链路、阅读流和壳层关系必须保持不变。

- `adjustmentValidationRules`
  说明生成后应满足哪些局部改造验收条件。

### 6.3 建模示例

下面是一份“局部改造 contract 的写法示例”，不是“典型页面增强类型定义”：

- `basePageType`：`table-basic`
- `retainedTypicalCharacteristics`：主工作区仍以表格为核心、分页 owner 不变、单一 whiteBody 不变
- `userAdjustmentIntent`：在主工作区上部增加一层用于切换同类数据集合的局部结构
- `allowedRegions`：主 whiteBody 中位于表格主体之前的受控局部区域
- `forbiddenRegions`：header owner、table owner、pagination owner、main scroll owner
- `insertPositionRule`：新增结构位于主工作区上部，不替代表头，不移动到分页之后
- `designSystemConstraints`：新增结构继续优先复用 HiUI5 与 `local-managed-runtime`
- `layoutPreservationRule`：保持原基础模板的壳层、阅读流和高度链
- `adjustmentValidationRules`：调整后页面仍然明确属于 `table-basic`

需要再次强调：

- 这个例子只是解释建模方式。
- 它不代表系统正在定义“table-basic 的固定增强位清单”。

## 7. 生成链路

### 7.1 输入归一化

先把提示词、原型截图、旧系统页面或其他已支持输入方式整理成统一页面描述，抽取结构事实，不直接跳代码。

### 7.2 基础页型判断

局部改造判断之前，必须先命中基础页型。如果基础页型不明确，整个局部改造链路不能继续。

### 7.3 contract 抽取

在基础页型明确后，根据当前用户诉求抽取 `pageAdjustmentContract`。

抽取重点不是给它命一个“增强类型名”，而是判断：

- 保留了什么
- 调整了什么
- 调整发生在什么相对区域
- 哪些结构不能动
- 调整后是否仍然属于原基础页型

### 7.4 冲突排查

在正式生成前，必须先排查以下冲突：

- contract 是否试图突破基础页型边界
- contract 是否试图改写壳层和 owner
- contract 是否已经把页面改造成第二个主结构
- contract 是否引入脱离 HiUI5 的局部设计系统

只要命中任一冲突，就不应继续按典型页面变体处理。

### 7.5 模板基础上的局部改造

正式生成时，执行顺序必须固定为：

1. 从基础页型官方模板起步。
2. 保留基础页型壳层、阅读流、滚动链与关键 owner。
3. 按 `pageAdjustmentContract` 对受控区域做局部改造。
4. 调整部分继续优先复用 HiUI5 与 `local-managed-runtime`。

当前执行层要求继续补充一个关键事实：

- 如果 contract 命中了当前生成器已经接通的受控区域锚点，生成器应直接把局部改造自动执行到基础模板中，而不是只输出一份“后续请人工实现”的说明。
- 如果 contract 没有命中稳定锚点，或当前页型还没有受控区域映射，生成器必须停止，并把原因明确写回执行结果。
- 这意味着 `pageAdjustmentContract` 已经不是纯说明性字段，而是执行层的结构操作输入。

禁止以下做法：

- 跳过基础模板自由拼装页面
- 把局部改造当成第二套典型页生成器
- 因为模板未直接覆盖，就改写整页主骨架
- 在局部改造区域内发明第二套基础 token 和视觉组件体系

## 8. 校验规则

### 8.1 校验顺序

局部改造页面的校验必须分两层执行：

- 先做基础页型校验
- 再做 `pageAdjustmentContract` 校验

如果两者冲突，以基础页型校验优先。

### 8.2 基础页型校验

基础页型校验继续复用既有合同，重点关注：

- `requiredShell` 是否保留
- provider 是否保留
- locked region 是否未被破坏
- forbidden token 是否未新增
- 主滚动链、whiteBody、表格、分页等 owner 关系是否仍然成立

### 8.3 局部改造校验

`pageAdjustmentContract` 校验重点关注：

- 调整是否发生在 contract 描述的受控区域
- 调整是否越过 contract 描述的禁止结构
- 插入位置是否符合 `insertPositionRule`
- 页面是否继续满足 `layoutPreservationRule`
- 改造部分是否继续满足 `designSystemConstraints`
- 最终页面是否仍然明确属于原基础页型

当生成器已经自动执行局部改造时，还需要额外检查：

- 执行层是否为当前 contract 选中了正确的受控区域锚点。
- 自动插入位置是否和 `insertPositionRule` 一致。
- 自动插入后的内容是否仍然没有破坏基础页型的主 owner、主滚动链和主要阅读流。

## 9. 风险与控制点

### 9.1 主要风险

当前建模方式的主要风险包括：

- 把字段名误读成固定枚举体系，重新走向增强类型目录化。
- 用少数案例替代能力定义，导致模型被示例牵着走。
- 只描述新增内容，不描述保留边界，导致验收失去依据。
- 默认把所有模板缺口都拉入局部改造路径，导致标准模板主链路被稀释。

### 9.2 控制原则

为降低上述风险，执行层应长期坚持以下原则：

- 只有基础页型明确时，才允许进入局部改造路径。
- 只有仍然保留基础页型大多数特征时，才允许形成 `pageAdjustmentContract`。
- 合同字段只描述当前需求相对基础模板的事实，不沉淀为固定增强类型表。
- 示例只作为说明材料，不作为产品能力的正式边界。

## 10. 结论

`典型页面变体` 在 `hiui-design v2` 中的正确落点，是“基础模板上的局部改造”这条生成路径；而在执行层，它被进一步建模为一份 `pageAdjustmentContract`。

这套建模方式的核心不是定义多少种增强类型，而是稳定回答四个问题：

- 基础页型是什么
- 哪些特征必须保留
- 当前诉求要局部改哪里
- 调整后如何继续符合 HiUI5 与典型页约束

只要这四个问题回答稳定，典型页面变体就可以作为能力层持续演进，而不会重新滑回“无限增补页型”或“模板失效后自由手写”的旧路径。
