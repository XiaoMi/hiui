# 业务理解与无 PRD 兜底

> **用途：** 在阶段 B 先建立“产品目标 + 核心用户 + 核心流程”的工作前提，再进入正式问题判断。  
> **原则：** 先做简洁任务理解，再模拟流程，最后用 checklist 收口补漏。

## 高层脚本入口

### 阶段 B 标准入口

优先使用：

```bash
python3 <SKILL_ROOT>/scripts/prepare_walkthrough_context.py \
  --precheck-json-file <A 阶段结果.json> \
  --prd-path <prd.md|prd.docx> \
  --signal-file <页面线索.txt> \
  --json
```

#### 返回重点

- `walkthrough_source`：本轮阶段 B 应按 `url / code / screenshot` 哪个口径继续
- `next_action=run_url_walkthrough / run_code_walkthrough`：业务理解已准备好，可继续
- `next_action=run_*_walkthrough_with_limited_business_claims`：业务线索偏弱，只报确定问题为主
- `status=needs_input`：不要硬写完整报告，先补最小必要信息

优先使用：

```bash
python3 <SKILL_ROOT>/scripts/build_business_context.py \
  --prd-path <prd.md|prd.docx> \
  --project-path <项目目录> \
  --signal-file <页面线索.txt> \
  --signal "按钮：新建合同" \
  --page-title "合同管理" \
  --route "/contracts" \
  --json
```

### 返回重点

- `status=ready`：任务理解卡可直接用于后续流程走查
- `status=degraded`：可继续，但应以“确定问题”为主，业务结论谨慎落笔
- `status=needs_input`：当前仍缺最小业务信息，优先澄清或降级
- `business_context`：可直接整理进 `report.json`
- `core_flows`：**必须生成 1–3 条** 作为阶段 B 的核心流程；若页面存在明确主按钮或行内主动作，不得留空
- 若已提供 `PRD / 产品文档`，但仍未能提炼出 `core_flows`，则脚本应直接返回 `needs_input`，不能继续正式走查
- `evidence_map`：回看每个判断主要来自哪些线索，避免把推断写成事实

## 输入优先级

按证据强弱读取，优先顺序如下：

1. PRD / 需求文档 / 飞书文档 / Markdown / PDF
2. 已运行页面与真实交互
3. 用户提供的截图序列
4. 代码中的路由、页面名、组件名、接口名、字段名、mock 数据
5. 页面标题、面包屑、导航、按钮文案、状态名、空状态 / 错误文案

## 任务理解卡

正式走查前，先产出一张简洁任务理解卡。它不是长分析，而是为了快速明确这页到底要先查什么。可写成内部笔记，也可直接整理进 `report.json`。

```json
{
  "business_context": {
    "source": "prd | inferred | mixed | unknown",
    "confidence": "high | medium | low",
    "product_goal": "",
    "primary_users": [],
    "core_tasks": [],
    "success_signal": "",
    "risk_points": [],
    "assumptions": [],
    "missing_information": []
  }
}
```

### 字段含义

- `source=prd`：主要依据 PRD / 需求文档
- `source=inferred`：未提供 PRD，主要依据页面 / 代码 / 截图反推
- `source=mixed`：既有文档，又结合现状核对
- `source=unknown`：关键业务信息不足，只能做降级走查

## 核心流程生成门禁

进入正式走查前，不能只写“这个页面看起来像做什么”，还必须把**要实际执行的核心流程**先列出来。

### 轻量要求

首轮任务理解默认只回答 4 个问题：

1. 这是什么页型 / 当前页最像什么场景
2. 这个页面最重要的 1–3 个任务是什么
3. 这次必须覆盖的核心流程是什么
4. 哪些动作属于低风险可直接跑，哪些动作可能要先确认

若这 4 个问题已经清楚，不需要再展开成长篇业务分析。

### 生成规则

1. 从页面级主动作生成流程
   例如：`新增 / 新建 / 创建 / 发布 / 导出 / 提交`
2. 从行内主动作生成流程
   例如：`查看 / 编辑 / 详情 / 删除 / 启停`
3. 若是列表 / 管理页：
   - 有页头主动作时，至少生成 1 条页头主动作流程
   - 有行内主动作时，至少生成 1 条行内动作流程
   - 两类都存在时，两类都必须覆盖
4. 若页面只存在搜索、筛选、分页等轻操作，也至少生成 1 条“查询 / 定位目标对象”流程

### 执行要求

- 核心流程不是写出来就算完成，后续必须按这些流程去实际走查
- 每条流程都要明确写出本次执行到了哪一步
- 若因为高风险停在提交前，也要把停留位置和原因写清楚
- **样式专项必须排在核心流程操作走查之后**，不能先看间距和留白，再回头补主流程

## 三种处理路径

### 1. 有 PRD / 需求文档

- 提炼：产品目标、主要用户、核心任务、关键流程、成功标志、高风险点
- 若是 `.docx`，可直接交给 `build_business_context.py --prd-path xxx.docx`
- 把 PRD 当作**预期目标**，不是最终事实
- 之后必须再和当前页面 / 截图 / 代码交叉核对
- 若发现冲突：
  - 报告中写清“文档预期”与“当前现状”
  - 不要直接把 PRD 当成唯一判定依据

### 2. 没有 PRD，但可从现有证据反推

优先从这些线索反推：

- 页面标题、导航、面包屑
- 主按钮 / 主操作名称
- 表格列名、表单字段、状态字段
- 空状态、成功提示、失败提示
- URL 路径、菜单分组、路由名
- 代码里的页面名、接口名、数据模型、mock 数据

这类场景推荐组合输入：

- `--project-path`：读项目里的页面、路由、可见文案线索
- `--signal-file`：放你手工整理的页面说明、截图可见文字、交互观察
- `--page-title / --route`：补页面标题和路径，帮助脚本推断场景

#### 典型反推问题

- 这个页面最像在支持什么业务目标？
- 谁最可能高频使用它？
- 用户来这里最可能要完成哪 1–3 个任务？
- 完成任务后，页面会给出什么结果或反馈？
- 哪一步失败代价最高？

### 3. 证据仍不足

若连以下三项都无法判断：

- `primary_users`
- `core_tasks`
- `success_signal`

则只允许二选一：

1. 问一句最小必要澄清  
   例：`这个页面最重要的任务更偏向查询、录入、审批，还是监控？`
2. 降级走查  
   只输出当前能确定的体验问题，并明确写出“业务信息不足，以下与业务相关判断暂不下确定结论”

## 用户流程模拟

任务理解卡完成后，必须先模拟并执行 1–3 条核心流程，再进入 checklist 收口。

每条流程至少回答：

1. 用户为什么进入这个页面
2. 第一步会看哪里、点哪里
3. 完成任务需要经过哪些步骤
4. 哪一步最容易卡住、迷失、误操作
5. 出错后能否恢复
6. 完成后是否收到明确反馈

对列表 / 管理页，额外要求：

- 先验证主流程，再看样式
- 若存在 `新增 / 创建 / 发布 / 导出` 这类页头主动作，不能漏掉
- 若存在 `查看 / 编辑 / 详情 / 删除` 这类行内动作，不能只停留在静态列表态
- 低风险且可回收的创建动作，默认应走完整闭环；只有高风险动作才先问用户

## 样式与结构的轻量顺序

主流程走完或已明确停在提交前后，再进入视觉判断。默认顺序是：

1. 先做结构四问快扫
2. 命中问题后再展开局部样式细查
3. 最后把结论回填进 checklist

结构四问只回答：

1. 页头到首屏内容有没有接住
2. 主白底外边距稳不稳
3. 多列有没有收口
4. 有没有大块无效空白

若 4 项都稳定，首轮不再做整页深扫；只检查主流程经过区域和用户明确指出的区域。

## 问题判断分层

### `confirmed`

- 有直接证据支撑
- 例如：页面已出现、交互已触发、代码逻辑已明确写死

### `inferred`

- 当前证据不能完全直接证明，但多个信号指向同一结论
- 可进入正式问题列表，但必须写清依据与假设

### `pending`

- 需要用户补充业务信息、补登录态、补交互或补截图
- 标题需显式包含「待交互验证」

## 报告规则

- 不要把“推断”写成“事实”
- 每个问题都要说明它处于哪个流程步骤、影响谁、为什么妨碍任务完成；这些信息可以直接融进问题描述里，不要求额外拆成独立字段
- 若无 PRD，必须在报告中说明“本次业务理解基于现有页面 / 代码 / 截图推断”
- 若关键流程无法完整走通，不要硬写业务结论；改写为“当前可确认的问题 + 待确认点”
- 若页面存在明确主按钮或行内主动作，但 `core_flows` 没有覆盖到，不应进入正式交付
