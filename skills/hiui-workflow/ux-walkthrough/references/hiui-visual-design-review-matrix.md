# hiui-design 视觉设计走查对照表

## 目的

本文件用于在 `hiui-design` 体系内做页面视觉走查、设计验收和一致性核对。

它重点回答四类问题：

- 当前页面是否仍然属于同一套 HiUI5 / `hiui-design` 视觉系统
- 页面结构是否仍然遵守统一页头、单一 `whiteBody`、单一主阅读流
- 组件是否仍然使用统一语义，而不是页面内自造一套皮肤
- 数据可视化是否仍然属于同一视觉体系，而不是独立 dashboard 皮肤

本文件已经把常用视觉细节、页型边界、组件默认值和图表主题约束内联整理，默认可作为独立走查文件直接使用。
若未来规则维护发生变更，应以最新受管规则为准，再同步回本文件。

## 使用方式

建议按下面顺序走查：

1. 先核对“全局视觉基线”
2. 再核对“跨页面共享结构”
3. 再按命中页型核对“页面级规范”
4. 再核对“组件级规范”
5. 若页面含图表，再追加“数据可视化专项”

推荐判定口径：

- `通过`：满足规则，且没有明显偏移
- `需确认`：规则本身满足，但存在书面例外、业务特例或宿主约束
- `不通过`：已偏离 `hiui-design` 基线，需修复或补例外说明

| 阴影策略 | 极轻或不用 | 优先靠描边、留白、分区节奏建立层级 | 依赖重阴影表达所有层次 | 全局基线 |
| 卡片圆角 | 紧凑卡 `8px`，标准主体 `12px` | 圆角使用有限档位 | 不同卡片圆角值漂移过多 | 全局基线 |
| 标准卡片内边距 | `20px` | 统一内容留白 | 页面局部卡片无依据改成 `24` 或 `28` | 全局基线 |
| 间距体系 | 默认采用 `2px` 递进 spacing scale；常用档位 `4 / 8 / 12 / 16 / 20 / 24 / 32` | 间距首先表达信息关系和层级，不只是留白 | 页面内出现大量无依据的自定义间距值 | 全局基线 |
| token 语义 | `0 / 2 / 4 / 8 / 12 / 16 / 20 / 24 / 32` 分别对应从无间距到较大间距的递进层级 | 走查时要看是否用统一梯度组织页面密度 | 相邻层级的间距无规律跳变 | 全局基线 |
| 元素间距 `4px` | 用于最强关联元素：`icon + text`、轻量状态、搜索图标与文案 | 视觉上应接近同一单元内部关系 | 明显分组关系却仍用 `4px` 贴死 | 全局基线 |
| 元素间距 `8px` | 用于紧凑同组元素：标题旁标签、筛选项、消息提示、轻按钮组 | 保持紧凑但有呼吸感 | 同组元素被拉得过散或挤得过紧 | 全局基线 |
| 元素间距 `12px` | 用于区块内次级分组：按钮组、卡片内信息块、标题与辅助操作 | 应体现“同区块内的小分组” | `12px` 被误用成大区块分隔 | 全局基线 |
| 元素间距 `16px` | 用于模块级或上下分布的信息块分隔 | 常见于描述列表、工作台模块、主区块竖向节奏 | 模块级内容仍用 `8px` 或 `12px` 导致层级不清 | 全局基线 |
| 元素间距 `24px` | 用于表单组或较大区块之间 | 应体现明显的阅读停顿 | 大区块之间仍然过于拥挤 | 全局基线 |
| 元素间距 `32px` | 用于高层级区域切换 | 应只出现在明显的大层级分离处 | 普通组件内部误用 `32px` | 全局基线 |
| 容器内填充 `8px` | 用于轻量、小体量容器 | 常见于文件列表项、下拉菜单项、轻量菜单 | 内容型容器误用 `8px` 导致局促 | 全局基线 |
| 容器内填充 `12px` | 用于小中型控件 | 常见于按钮、筛选器、`Select`、`Tooltip` | 大容器仍沿用 `12px` 导致信息贴边 | 全局基线 |
| 容器内填充 `20px` | 用于内容型容器和主体容器 | 常见于卡片、弹窗、折叠面板、模态框、抽屉、白底主体区 | 页面主体或内容容器内边距明显不足 | 全局基线 |
| 间距使用方式 | 元素间距优先 `gap`，容器安全距离优先 `padding` | 先看容器层和组件层是否使用了正确职责 | 大量靠零碎 `margin` 拼节奏 | 全局基线 |
| Host 字体基线 | 根节点默认 `14px / 22px / 400 / #1A1D26`；宿主重置链至少应保证 `font-family`、`font-size`、`line-height`、`color` 不被全局污染 | 宿主全局字体规则不能污染典型页 | 页面整体字号突然变大 / 变小 | Host 基线 |

## 二、跨页面共享结构

| 检查项 | 标准语法 | 走查重点 | 常见不通过信号 | 归属层 |
| --- | --- | --- | --- | --- |
| 统一页头 | 必须存在统一 `PageHeader` | 页面级标题与主操作应由统一页头承接 | 局部模块标题替代页面标题 | 共享结构 |
| 单一主工作区 | 必须存在唯一 `whiteBody` | 主内容 owner 只能有一个 | 通过多层白卡伪造第二主工作区 | 共享结构 |
| 单一主阅读流 | 页面能说清“从哪里开始、如何完成任务” | 主阅读流要唯一、清晰 | 多个区域都试图担当主入口 | 共享结构 |
| 单一主结构 | 筛选、表格、底栏、详情流都服从同一主结构 | 复杂不等于多主结构 | 左右、上下多个区同时争抢主任务定义权 | 共享结构 |
| primaryRegion 唯一 | 只能有一个 `primaryRegion` | 先判断主任务区再看 supporting 区 | supporting 区变成第二主页面 | 共享结构 |
| supportingRegion 边界 | supporting 区只能补充，不替代主区 | 摘要卡、支撑表格、辅助面板只做支撑 | supporting 区抬升成另一套主结构 | 共享结构 |
| 页面变化方式 | 优先变化工作区组合，不变化视觉体系 | 看页面是否仍“像同一产品” | 每个页面像不同后台皮肤 | 共享结构 |
| surface 关系 | 默认保持灰底外槽 + 白底主体 | 结构优先于装饰 | 局部用彩色大底 / 强装饰背景重建结构 | 共享结构 |
| spacing / token 控制 | 页面本地样式默认只做布局；没有明确设计依据时不新增页面本地视觉 token | 页面变化应优先发生在布局和内容组合，不是新建一套局部 token | 局部新增视觉 token | 共享结构 |
| 组件语义一致 | 按钮、输入、Tag、表格、详情语义一致 | 先看组件一致性再看页面相似性 | 同类组件跨页表现分叉 | 共享结构 |
| 图表属于设计系统 | 图表必须回指统一主题和色板 | 图表不是独立视觉子系统 | 图表页像另一个 dashboard 产品 | 共享结构 |

## 三、典型页面共性规范

### 3.1 典型页面通用规则

| 检查项 | 标准值 / 标准语法 | 走查重点 | 常见不通过信号 | 归属层 |
| --- | --- | --- | --- | --- |
| 页面实现起点 | 标准典型页必须从受管官方母版或固定页壳起步 | 先判页型，再落到对应壳层，不从空白页发明结构 | 直接从空白页、旧业务页、普通后台页手拼典型页 | 典型页共性 |
| 固定页壳优先 | 列表、统计、树表、左树右表、抽屉、全页编辑、全页详情都必须保留固定页壳 | 典型页首先是壳层语言，不是组件自由组合 | 把固定页壳拆掉，再用 `Card` 或灰底容器重搭 | 典型页共性 |
| 业务替换边界 | 标准典型页默认只替换标题、查询字段、表格列、表单字段、详情字段、请求、按钮、mock 数据、跳转目标 | 业务替换应发生在受控槽位，不重写底层结构 | 只改标题却保留示例业务词，或直接重写整页结构 | 典型页共性 |
| 受控重构边界 | 独立能力页可整体生成内容区，但仍要保留固定页头、`whiteBody`、主滚动和受管 owner | 看是否清楚哪些是允许重构面，哪些是锁区 | 以重构为名改掉壳层、滚动链、分页 owner | 典型页共性 |
| 锁区概念 | `header owner`、`whiteBody owner`、`main scroll owner`、`table owner`、`pagination owner`、`drawer body owner`、`footer owner` 默认属于锁区 | 走查时先判断 owner 是否仍然成立 | 壳还在，但 owner 已经换了 | 典型页共性 |
| 单一白底主体 | 典型页主内容默认落在单一 `whiteBody` 中 | 白底主体应是整页主要内容承载层 | 再造第二个白底主体，或把主体拆成多张平级大白卡 | 典型页共性 |
| 单一滚动链 | 表格类、全页编辑、全页详情默认只保留一条主滚动链 | 滚动交给受管壳层，不在业务页额外补滚动 | 业务页根或中间层额外加 `overflow-y:auto` | 典型页共性 |
| 高度链 | 宿主出口到典型页根应保持连续 `display:flex`、`flex:1 1 0%`、`min-height:0`，必要时 `overflow:hidden` | 白底不铺满、分页下露灰底、双滚动通常先看高度链 | 用 `min-height:100vh`、额外白卡或额外滚动层硬补 | 典型页共性 |
| 页头桥接 | 正式宿主若存在保留页头槽，应通过受管 portal / host provider 承接 `PageHeader` | 页头应挂到宿主 header 槽，而不是回落在内容区 | 宿主页头空着，内容区里又出现一份页头 | 典型页共性 |
| 页头角色 | `PageHeader` 负责页面识别、返回和页面级轻操作 | 页头不是表单主体、说明区或局部模块容器 | 在内容主体内再放第二个页头 | 典型页共性 |
| 页头主操作位置 | 页面级主操作默认位于 `PageHeader` 右侧，主按钮在最右 | 主操作应清晰、稳定、可预测 | 主操作跟标题挤在左侧，或漂到主体中部 | 典型页共性 |
| 菜单标题一致性 | 菜单标题与 `PageHeader title` 保持一致 | 导航命名和页面识别保持统一 | 菜单名和页头标题脱节 | 典型页共性 |
| 页面标题字重 | 页面标题默认保持 `600` | 典型页标题层级要稳定 | 某些页标题加粗到另一套体系，或权重过弱 | 典型页共性 |
| 本地样式边界 | 页面本地样式默认只做布局和允许槽位样式 | 业务页面不负责重建设计系统 | 用页面本地 CSS 重造按钮、输入、表格、卡片皮肤 | 典型页共性 |
| 全局样式边界 | 业务页面文件不得改 `:root`、`html`、`body`、`#root`、`#__next`、`#app`、`h1-h6` 等全局选择器 | 全局排版与宿主基线由公共层承接 | 页面为了纠偏字号或留白直接改全局 | 典型页共性 |
| 预览资产边界 | preview / 示例资产只做参考，不进入正式业务输出 | 正式页面应落在业务目录，不走 preview 路由树 | 正式页面直接引用 preview 组件、示例壳或示例辅助功能 | 典型页共性 |
| 视觉 token 边界 | 没有明确设计依据时，不新增页面本地视觉 token | 典型页共享同一套颜色、字阶、圆角、间距语法 | 某页单独新增颜色、圆角、阴影变量 | 典型页共性 |
| 交付说明边界 | 接口未接入说明、mock 说明、生成说明、测试说明不得作为页面常驻 UI | 页面常驻区只承载业务内容 | 页面里挂“当前为示例 / 稍后接入接口”公告条 | 典型页共性 |
| 组件来源边界 | 基础视觉组件应继续回到 HiUI5 与受管页壳公开能力 | 典型页首先复用系统语义，不自由选型 | 在业务页用另一套视觉组件替代受管语义 | 典型页共性 |
| 旧视觉残留清理 | 不允许残留旧版本选择器、变量、旧演示文案 | 典型页应统一落在当前视觉体系 | 页面里混入旧样式类名、旧版本 token、旧演示词 | 典型页共性 |
| 变体处理方式 | 典型页的变化优先通过同一页型内变体、局部调整或 supporting section 表达 | 先保住基础页型，再处理业务差异 | 页面一变化就跳出原页型，重新发明结构 | 典型页共性 |
| 自检视角 | 先看页型是否正确，再看壳层、owner、业务槽位、滚动链、视觉语法是否仍成立 | 先判像不像这个页型，再判细节是否一致 | 只看像不像，不看 owner 和边界；或只看代码结构，不看视觉结果 | 典型页共性 |

### 3.2 典型页面描述摘要

走查典型页面时，建议先看三件事：

1. 主任务是什么：检索列表、查看详情、完成编辑，还是做状态反馈
2. 主承载体是什么：表格、抽屉、全页表单、全页详情流，还是单一反馈面板
3. 主阅读流是什么：页面应先看哪里、再做什么、最后在哪里收口

| 页型 | 页面描述 | 主任务与主阅读流 | 常见误判边界 | 归属层 |
| --- | --- | --- | --- | --- |
| 普通表格 | 最常规的后台列表页，以检索、浏览、批量操作和翻页为主 | 页头 -> 筛选 -> 表格 -> 分页；主任务是列表检索和结果处理 | 不要因为有几个筛选项就误判成数据统计表；不要因为有层级字段就误判成树页 | 典型页描述 |
| 数据统计表 | 在列表任务之前补一层关键指标摘要，但最终仍以表格为主承载体 | 页头 -> 指标卡 -> 筛选 -> 表格 -> 分页；主任务仍是列表经营与数据查看 | 不要退回普通表格；若图表承担主信息载体，不应继续留在统计表 | 典型页描述 |
| 树形表格 | 树结构收在表格首列内部展开，本质仍是一张表 | 页头 -> 筛选 -> 表内树 -> 分页；主任务是层级数据查看与操作 | 不要误判成左树右表；如果左侧树负责驱动右侧表，就已经不是树形表格 | 典型页描述 |
| 左树右表 | 左侧树负责对象选择或范围切换，右侧表负责结果浏览和操作 | 左树选择 -> 右栏标题 -> 筛选 -> 表格 -> 分页；主任务是“树选择驱动右侧列表” | 不要误判成树形表格；也不要把它拆成两个互不相关的大白卡 | 典型页描述 |
| 抽屉表单 | 少量字段编辑在抽屉内完成，不打断列表或原页面上下文 | 页头或列表触发 -> 抽屉标题 -> 表单 -> footer；主任务是轻量编辑 | 不要为了字段稍多就仍硬塞抽屉；字段很多、分组复杂时应切到全页编辑 | 典型页描述 |
| 抽屉详情 | 少量只读信息在抽屉内查看，保留原列表或原页面上下文 | 页头或列表触发 -> 抽屉标题 -> 描述区；主任务是轻量查看 | 不要误用成全页详情；长文本多、分组多时不应继续留在抽屉 | 典型页描述 |
| 全页编辑 | 字段多、流程长、分组明显的编辑场景，需要完整工作区和底部操作收口 | 页头 -> 表单滚动区 -> 固定底栏；主任务是整页完成编辑并在底栏提交 | 不要降级成抽屉表单；也不要退化成“灰底 + 单张大白卡”的普通表单页 | 典型页描述 |
| 全页详情 | 分组较多的只读详情页，以稳定阅读和结构化浏览为主 | 页头 -> 白底详情流 -> supporting sections；主任务是分组阅读与理解对象全貌 | 不要套用抽屉详情语法；也不要拆成多张平级摘要卡抢主结构 | 典型页描述 |
| 异常反馈页 | 页面主内容是空状态、失败、无权限、建设中等反馈，不再以列表或表单为主 | 页头 -> 居中反馈面板 -> 动作按钮；主任务是识别当前状态并继续下一步 | 如果原页主体仍是列表、表单或详情，只是局部出现空态，不要改判成异常反馈页 | 典型页描述 |

| 主图强调方式 | `chartGridFeatured` 跨两列；在移动端回落为单列跨度 | 通过同一 grid 中的 span 强调主图 | 为强调主图另起第二套布局系统 | 图表布局 |
| 图表卡 fill contract | 图表项容器 `display:flex`；子项拉伸填满；最小高约 `280px` | 卡片同一行高度要稳定 | 仅靠图表自然撑高，导致卡片高低参差 | 图表布局 |
| 指标卡默认表达 | 标题 + 主值；迷你图可选 | 无业务依据时保持克制 | 默认加彩色顶边、角标、同环比、渐变条 | 图表布局 |
| 指标卡样式 | 白底、`1px` 描边、`8px` 圆角、`16px` 内边距、内部 `gap: 10px` | 与统计页指标卡同一体系 | 单张卡自造装饰语言 | 图表布局 |
| 图表卡结构 | 固定 `chartHeader -> chartContent` | header 固定，body 拉伸 | 每张图自由拼 DOM、标题区高度漂移 | 图表布局 |
| 尾行收口 | 生成前先做 `slotPlan / rowFillDecision` | 避免最后一行孤图 | 最后一张图单独掉到一行 | 图表布局 |

## 八、建议输出格式

做页面设计走查时，建议最终结论按下面结构输出：

| 维度 | 结论 | 问题级别 | 说明 |
| --- | --- | --- | --- |
| 全局视觉基线 | 通过 / 需确认 / 不通过 | P0 / P1 / P2 / P3 | 例如“主交互色仍为 HiUI Blue，未发现第二主色” |
| 跨页面共享结构 | 通过 / 需确认 / 不通过 | P0 / P1 / P2 / P3 | 例如“存在第二个 whiteBody，需回收到主工作区” |
| 页型规范 | 通过 / 需确认 / 不通过 | P0 / P1 / P2 / P3 | 例如“当前页面更像统计页型，但实现退化成普通列表页” |
| 组件语义 | 通过 / 需确认 / 不通过 | P0 / P1 / P2 / P3 | 例如“QueryFilter 行内筛选被改成 showLabel=true” |
| 数据可视化专项 | 通过 / 需确认 / 不通过 | P0 / P1 / P2 / P3 | 例如“图表色板已回退默认主题，需接回受管图表主题” |

## 九、问题级别对齐建议

> 详细定级以 `severity-rubric.md` 为准；本节只给 HiUI 视觉专项的落地口径。

### 先分清两类输出

1. `style_review.hiui_sections`
   - 用来写 HiUI 专项结论
   - 允许使用 `P0 / P1 / P2 / P3`
2. 正式 `issues[]`
   - 用来写真正需要单独修的用户问题
   - **仍只使用 `P0 / P1 / P2`**

### HiUI 专项里的级别建议

| 对照项 | P0 | P1 | P2 | P3 |
| --- | --- | --- | --- | --- |
| 全局视觉基线 | 主色、危险色、主体结构色严重错位，影响状态判断 | 主次层级、颜色灰阶、主体底色明显漂移，持续干扰阅读 | 局部颜色、字重、圆角、间距不统一 | 轻微零散偏差，建议后续统一收口 |
| 跨页面共享结构 | 第二主工作区 / 第二主滚动 / 主阅读流断裂 | 页头、主区、supporting 区职责明显混乱 | 结构边界略松但不阻断 | 轻微节奏或留白问题 |
| 页型规范 | 页型错误已影响任务承载 | 页壳、owner、滚动链、底栏等明显偏离 | 页型内局部视觉语法偏移 | 轻微页型细节漂移 |
| 组件语义 | 主操作 / 危险语义 / 状态语义错置 | 按钮、Tag、筛选、详情语法明显分叉 | 组件样式不齐但仍可理解 | 局部皮肤或细节收口项 |
| 数据可视化专项 | 图表主题或阅读流错误，影响读数与分析 | 色板、主次图、布局明显偏离 | 卡片、轴线、顺序色板不够统一 | 轻微图表主题收口项 |

### 何时把专项结论升级成正式问题

- 已经影响用户判断主次、状态或风险
- 已经让页面不像同一产品，用户需要重新学习
- 已经破坏页型承载，影响主要任务流
- 已经让图表读数、趋势判断或列表结果理解出现明显偏差

若只是体系一致性上的轻偏差，不必强行升级成正式问题，留在专项结论里即可。
