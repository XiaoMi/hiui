# 体验问题示例库

每个问题包含：位置、描述、理由、改进方案（含样式参数）。
这些示例主要用于帮助判断问题内容和改进方向；最终报告输出时，问题标题仍必须使用 `序号. [P级]标题` 格式。

## URL 走查示例

### [P0] 主操作不可见 — 核心 CTA 被折叠

**位置**：`https://example.com/dashboard` → 页面右上角

**问题描述**：首页核心操作"新建工单"被收进「更多」下拉菜单中，首屏不可见。用户需要额外一次点击才能找到入口。

**设计理由**：Fitts 定律——目标越大、越靠近用户常规操作区域，到达时间越短。核心操作应始终可见，不应隐藏在次级菜单中。

**用户影响**：高频操作入口隐蔽，新用户可能找不到创建入口，降低功能发现率。

**改进方案**：
- Before："新建工单"在「更多」菜单内，需 2 步操作
- After："新建工单"作为主按钮（Primary Button）直接展示在页面右上角
- 样式参数：
  - 主按钮：height 40px，padding 0 24px，background #1677ff，border-radius 8px
  - 位置：页面标题右侧，与筛选栏对齐

---

### [P1] 移动端适配差 — 表格横向滚动无提示

**位置**：`https://example.com/orders` → 订单列表

**问题描述**：桌面端 10 列表格在移动端（375px）直接溢出，需要横向滚动，但无滚动指示器，用户不知道右侧还有内容。

**设计理由**：用户注意力有限，无提示的溢出等于信息丢失。移动端应通过列优先级控制、响应式布局或卡片式展示来解决。

**改进方案**：
- Before：表格 10 列平铺，移动端溢出，无滚动提示
- After：移动端仅展示 5 列核心字段，其余收入展开面板
- 样式参数：
  - 移动端表格：min-width 移除，改用 overflow-x: auto + 渐变遮罩提示右侧有内容
  - 遮罩：width 24px，background linear-gradient(to right, transparent, #fff)

## 截图走查示例

### [P1] 信息层级混乱 — 标题与正文无主次

**位置**：截图 `order-detail.png` → 页面顶部区域

**问题描述**：订单详情页标题「订单详情」与下方副标题「订单号：ORD-20260507-001」字号、颜色相同，无法区分信息层级。

**设计理由**：视觉层级是信息架构的直接体现。标题和副标题应在字号、字重、颜色上有明确区分，帮助用户快速识别页面主题和关键信息。

**改进方案**：
- Before：标题 font-size 16px color #333，副标题 font-size 16px color #333
- After：标题 font-size 20px font-weight bold color #1a1a1a，副标题 font-size 14px font-weight normal color #666 margin-top 8px
- 样式参数：
  - 标题：font-size 20px，font-weight 600，color #1a1a1a，line-height 28px
  - 副标题：font-size 14px，font-weight 400，color #666666，line-height 22px，margin-top 8px
  - 标题与副标题间距：margin-bottom 24px

**位置**：截图 `user-profile.png` → 联系信息区域

**问题描述**：用户手机号 13812345678 完整展示，无脱敏处理。

## 流程问题示例

### [P0] 导航层级过深 — 菜单嵌套超 3 级

**位置**：侧边导航系统

**问题描述**：菜单嵌套 4 级甚至 5 级，用户需要多次点击才能触达目标页面，且难以返回上层。

**设计理由**：信息架构深度直接影响可达性。菜单层级过深会增加认知负担和操作路径，宜尽量控制在清晰、可回退的范围内。

**改进方案**：
- Before：一级 > 二级 > 三级 > 四级 > 目标页面（4 步+）
- After：合并低频四级菜单到三级，或通过全局搜索直达；一级菜单 ≤9 个，二三级 ≤16 个

---

### [P1] 表单无分组 — 10+ 字段平铺堆砌

**位置**：录入表单

**问题描述**：表单包含 15 个字段（姓名、手机、邮箱、地址、公司、职位、备注...）全部平铺展示，无分组、无分隔，用户一次面对过多输入项。

**设计理由**：Chunking（组块化）——人脑工作记忆容量有限，将信息分组后可显著降低认知负荷。字段较多时应按业务逻辑分组。

**改进方案**：
- Before：15 个字段单列平铺
- After：按逻辑分为"基本信息"（≤6 个）、"联系方式"（≤4 个）、"附加信息"（≤5 个）三组，每组有分组标题
- 样式参数：
  - 分组标题：font-size 14px，font-weight 600，color #1a1a1a，margin-bottom 16px
  - 分组间距：margin-bottom 32px
  - 组内字段间距：margin-bottom 20px

## 流程问题示例

### [P0] 流程死胡同 — 删除后无法恢复

**位置**：`src/views/UserList.vue` → 批量删除按钮

**问题描述**：用户选中多条记录点击删除后，数据直接从列表消失，无回收站、无撤销入口、无确认弹窗。

**设计理由**：删除是不可逆操作。Nielsen 可用性启发式 #3（用户控制与自由）明确指出，用户需要"紧急出口"来离开非预期状态。批量删除影响范围大，误操作成本极高。

**改进方案**：
- Before：点击删除 → 数据消失
- After：点击删除 → 二次确认弹窗（含数量提示）→ 删除后 toast 提示"已删除，可在回收站恢复"→ 提供 5s 撤销入口
- 样式参数：
  - 确认弹窗：宽度 400px，圆角 8px，遮罩 rgba(0,0,0,0.45)
  - 撤销按钮：height 32px，padding 0 16px，color #1677ff，font-size 14px
  - toast：距顶部 24px，背景 #fff，阴影 0 4px 12px rgba(0,0,0,0.08)

---

### [P1] 操作步骤冗余 — 修改个人信息需 5 步

**位置**：`src/pages/profile/Edit.tsx`

**问题描述**：修改头像需：点击编辑 → 选择图片 → 裁剪 → 确认 → 保存，共 5 步。其中"确认裁剪"和"保存"可合并。

**设计理由**：Hick 定律——选择越多、步骤越多，决策时间越长。高频操作（改头像）应尽量缩短路径，减少认知负担。

**改进方案**：
- Before：编辑 → 选图 → 裁剪 → 确认 → 保存（5步）
- After：点击头像 → 直接弹出裁剪 → 保存（3步），裁剪确认与保存合并
- 样式参数：
  - 裁剪弹窗：全屏（移动端）/ 480×400px（桌面端）
  - 保存按钮：fixed 在弹窗底部，height 48px，background #1677ff

## 交互问题示例

### [P2] 弹窗关闭方式单一 — 仅支持点击 X

**位置**：模态弹窗 / 对话框

**问题描述**：弹窗只能通过右上角 X 按钮关闭，不支持 Esc 键和点击蒙层关闭。

**设计理由**：用户操作习惯多样化——键盘用户依赖 Esc，鼠标用户习惯点蒙层。关闭路径过少会增加操作摩擦。

**改进方案**：
- Before：仅 X 按钮可关闭
- After：同时支持 X 按钮 + Esc 键 + 蒙层点击（模态弹窗可选禁止蒙层关闭）
- 样式参数：
  - 蒙层：rgba(0,0,0,0.45)
  - Esc 响应延迟：< 100ms

---

### [P1] 禁用按钮无解释 — 用户不知为何不可操作

**位置**：按钮组件

**问题描述**：按钮处于 Disabled 状态时，视觉上仅降低透明度，用户 Hover 时无任何提示，不知道为什么不能点。

**设计理由**：可发现性与可理解性——用户遇到禁用按钮会产生困惑："是我没填完？还是系统有问题？"应尽量直接说明禁用原因。

**改进方案**：
- Before：按钮变灰，无提示
- After：按钮 opacity 0.4 + cursor: not-allowed，Hover 时 Tooltip 显示原因（如"请先填写手机号"）
- 样式参数：
  - Tooltip：background #333，color #fff，font-size 12px，padding 4px 8px，border-radius 4px

---

### [P1] 错误提示不友好 — 只说"操作失败"

**位置**：表单提交 / API 错误反馈

**问题描述**：接口返回错误后，页面仅显示"操作失败"或错误码，不告知原因和解决路径。

**设计理由**：错误恢复性——Nielsen 启发式 #9（帮助用户识别、诊断和从错误中恢复）。用户看到"操作失败"后不知所措，只能重试或放弃。

**改进方案**：
- Before：toast 提示"操作失败"
- After：toast 提示"提交失败：手机号格式不正确，请检查后重试"，错误字段红框高亮 + 下方红字说明
- 样式参数：
  - 错误文字：font-size 12px，color #ff4d4f，margin-top 4px
  - 错误边框：border 1px solid #ff4d4f

## 交互问题示例

### [P1] 加载状态缺失 — 提交表单无反馈

**位置**：`src/components/OrderForm.jsx` → 提交按钮

**问题描述**：用户点击"提交订单"后，按钮无 loading 态、页面无遮罩、无进度提示。用户不确定是否已提交，可能重复点击。

**设计理由**：Nielsen 可用性启发式 #1（系统状态可见性）——用户执行操作后，系统必须在合理时间内给出反馈。无反馈导致用户焦虑和重复操作。

**改进方案**：
- Before：点击提交 → 按钮无变化 → 用户反复点击
- After：点击提交 → 按钮变为 loading 态 + 文字"提交中..." → 页面遮罩禁止操作 → 完成后跳转成功页
- 样式参数：
  - Loading 按钮：保持原尺寸，文字替换为 Spin 图标 + "提交中..."，opacity 0.7
  - 遮罩：rgba(255,255,255,0.6)，z-index 1000
  - 禁止重复提交：按钮 disabled 直到请求完成

---

### [P2] 空状态缺失 — 搜索无结果白屏

**位置**：`src/views/Search.vue` → 搜索结果列表

**问题描述**：搜索关键词无匹配时，列表区域完全空白，无任何提示。

**设计理由**：空状态是用户旅程中的关键触点。空白让用户困惑："是没加载完？还是真的没结果？"好的空状态应解释原因并提供出路。

**改进方案**：
- Before：空白区域
- After：居中展示空状态插画 + 文字"未找到相关结果" + 建议"试试其他关键词" + 清除筛选按钮
- 样式参数：
  - 插画尺寸：120×120px，opacity 0.6
  - 主文字：font-size 16px，color rgba(0,0,0,0.65)，margin-top 16px
  - 副文字：font-size 14px，color rgba(0,0,0,0.45)，margin-top 8px
  - 按钮：margin-top 16px，height 32px

## 样式问题示例

### [P1] 色彩语义不一致 — 同色不同义

**位置**：全局色彩系统

**问题描述**：蓝色在不同页面分别表示"进行中""可点击""已选中"三种含义；红色既表示"错误"又表示"删除"。用户无法通过颜色建立一致的心理模型。

**设计理由**：语义一致性——颜色是信息传达的高速通道，同色异义会直接导致认知混乱。功能色应保持语义统一：绿=成功、红=错误/危险、蓝=信息/进行中、黄=警告、灰=禁用。

**改进方案**：
- Before：蓝色混用（链接蓝 #1677ff、选中蓝 #1890ff、信息蓝 #40a9ff）
- After：统一 Primary Blue #1677ff，所有可交互元素和信息提示共用同一色值；删除/危险统一用 #ff4d4f
- 样式参数：
  - 建立 Design Token 体系：primary / success / warning / error / disabled 各一个色值

---

### [P2] 数字未使用等宽字体 — 列数据对不齐

**位置**：数据表格 / 统计卡片

**问题描述**：表格中金额列使用默认字体，"1,234" 和 "89,012" 的字符宽度不一致，纵向无法对齐，难以比较大小。

**设计理由**：数据可读性——等宽字体（Tabular Figures）能保证每个数字占据相同宽度，是数据密集型界面的常见做法。

**改进方案**：
- Before：font-family: inherit（使用比例字体）
- After：数字区域 font-variant-numeric: tabular-nums 或 font-family: "SF Mono", "Menlo", monospace
- 样式参数：
  - font-variant-numeric: tabular-nums
  - font-feature-settings: "tnum"

---

### [P2] 键盘不可操作 — 仅支持鼠标交互

**位置**：自定义交互组件（下拉菜单、树形选择、日期选择器等）

**问题描述**：自定义组件不支持 Tab 切换焦点、Enter 确认、Esc 关闭、方向键导航，完全依赖鼠标操作。

**设计理由**：无障碍与效率——键盘操作是无障碍的基本要求（WCAG），同时也是高效用户的常用方式。所有交互元素都应尽量支持键盘操作。

**改进方案**：
- Before：组件仅响应鼠标事件
- After：支持 Tab 进入/退出、Enter 选择、Esc 关闭、↑↓ 导航选项
- 样式参数：
  - focus 态：outline: 2px solid #1677ff，outline-offset: 2px

## 样式问题示例

### [P1] 信息密度过高 — 表格列数过多

**位置**：`src/components/DataTable.tsx` → 订单列表

**问题描述**：订单表格展示 12 列（订单号、商品名、数量、单价、总价、状态、下单时间、支付时间、发货时间、收货时间、操作、备注），横向需要滚动，信息拥挤。

**设计理由**：米勒定律——人类短期记忆容量为 7±2 项。表格列数过多增加认知负荷，用户难以快速定位关键信息。应区分"必须展示"和"可展开查看"的信息。

**改进方案**：
- Before：12 列平铺，横向滚动
- After：核心列 6 列（订单号、商品名、状态、总价、下单时间、操作），其余 6 列收入"详情"展开面板
- 样式参数：
  - 表格：width 100%，min-width 800px
  - 列宽分配：订单号 120px、商品名 auto、状态 100px、总价 100px、时间 160px、操作 100px
  - 行高：height 56px（含上下 padding 12px）
  - 字号：表头 14px bold，内容 14px regular

### [P2] 间距无规律 — 元素间距不统一

**位置**：`src/pages/dashboard/index.css`

**问题描述**：卡片间距混用 10px、12px、15px、16px，无统一规律。

**设计理由**：一致性是可用性基础（Nielsen 启发式 #4）。间距不统一导致视觉节奏混乱，页面显得"不专业"。应建立 4px 或 8px 基线网格。

**改进方案**：
- Before：margin: 10px / padding: 12px / gap: 15px
- After：统一使用 8px 倍数体系
- 样式参数：
  - 卡片间距：gap 16px（2×8px）
  - 卡片内边距：padding 24px（3×8px）
  - 标题与内容间距：margin-bottom 16px
  - 段落间距：margin-bottom 12px（1.5×8px，允许半倍数）

### [P2] 图片显示异常 — 变形 / 模糊 / 裂图

**位置**：图片容器（列表卡片 / 详情页 / 头像等）

**问题描述**：图片被拉伸变形，未锁定宽高比；在高分屏上发虚、有锯齿；加载失败时直接显示裂图图标或空白，破坏页面完整性。

**设计理由**：好的体感——图片质量会直接影响页面的专业感和可信度。图片一旦变形、模糊或加载失败，用户很容易第一眼就感受到页面“做得不精细”。

**改进方案**：
- Before：图片按容器强行拉伸，失败后直接裂图或留白
- After：容器固定比例，图片裁切填充；高分屏资源使用 2x 倍图或 SVG；失败时回退到占位图，保持版面稳定
- 样式参数：
  - 图片容器：aspect-ratio 固定，如 `1 / 1`、`4 / 3`、`16 / 9`
  - 图片适配：`object-fit: cover`
  - 高清资源：图标/封面提供 2x 倍图，或优先使用 SVG
  - 异常兜底：`onerror` 回退占位图，容器宽高不变

### [P2] Logo 使用不规范 — 未遵循品牌标准样式

**位置**：页面中使用品牌 Logo 的区域（Header / Footer / 启动页 / 关于页等）

**问题描述**：页面中的品牌 Logo 没有使用标准样式，出现颜色被修改、比例被拉伸、Logo 被旋转、使用空心线框样式、添加阴影或边框、安全空间内塞入其他元素、放在难以识别的背景上等问题。

**设计理由**：好的体感——Logo 是品牌识别最核心的元素之一。只要用法不规范，就会削弱品牌一致性，也会让页面显得不够专业、不够可信。

**改进方案**：
- Before：Logo 被二次加工，颜色、比例、背景适配都不统一
- After：统一使用品牌规范提供的标准 Logo 文件，不做额外变形或装饰，并为 Logo 保留安全空间
- 样式参数：
  - 资源来源：仅使用品牌规范提供的标准 SVG / PNG
  - 禁止项：禁止改色、拉伸、压缩、旋转、加阴影、加边框、加装饰
  - 安全空间：Logo 四周保留最小留白，避免与文字或图形贴得过近
  - 背景要求：避免放在高噪点、低对比或干扰识别的背景上
