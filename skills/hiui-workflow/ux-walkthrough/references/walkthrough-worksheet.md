# 走查工作表（阶段 B 内部用）

> **用途：** 阶段 B 先建立任务理解，再按核心流程走查，最后用 checklist 收口补漏。
> **不写入**对话报告正文或 docx 主文；结论同步到 `report.json` 与 `checklist_coverage`。

## 使用规则

1. 必须先填 **任务理解卡** 与 **核心流程卡**，再执行结构快扫和 Batch 1 → 4
2. 每批填完后自检：本批 ID 是否都已有一行判定？
3. `checklist_coverage` 取值：
   - `pass: <你怎么验证的，≥8 字>` — 已检查且无问题
   - `issue` — 有问题，须在 `issues[]` 体现
   - `pending: <缺什么证据>` — 须写「待交互验证」issue
   - `n/a: <为何不适用>` — 仅当该条对当前页面/模式确实无检查对象
4. **禁止**无证据的裸 `pass`；**禁止**未读 checklist 条目就整批标 pass
5. **禁止**只按 checklist 找问题，不先回答“用户是谁、要完成什么、什么算成功”
6. **禁止**跳过主流程：若页面存在明确主按钮或行内主动作，核心流程卡必须覆盖到
7. **禁止**先做样式专项再补主流程；顺序必须是“核心流程 → 结构快扫 → 命中再展开 → checklist 收口”
8. `checklist` 主要用于回填证据与补齐漏项，不作为第二轮整页深扫

|------|------|----------|

| 成功标志 | | |
| 高风险环节 | | |
| 关键假设 | | |
| 缺失信息 | | |

**本卡规则：**

- 有 PRD：先按 PRD 提炼，再和现状核对
- 无 PRD：从页面 / 截图 / 代码证据反推
- 若 `主要用户 / 核心任务 / 成功标志` 三项仍不清晰，只能最小澄清或降级走查
- 首轮优先写短，不要求展开成长篇说明；只要能明确页型、主任务、核心流程和风险分级即可

## 核心流程卡

| 流程名 | 流程类型 | 用户目标 | 关键步骤 | 执行到哪一步 | 当前阻塞 / 风险 | 结论状态 |
|--------|----------|----------|----------|--------------|-----------------|----------|
| 流程 1 | 页头主动作 / 行内动作 / 查询流程 | | | 已完成 / 停在提交前 / 待确认 | | confirmed / inferred / pending |
| 流程 2 | 页头主动作 / 行内动作 / 查询流程 | | | 已完成 / 停在提交前 / 待确认 | | confirmed / inferred / pending |
| 流程 3 | 页头主动作 / 行内动作 / 查询流程 | | | 已完成 / 停在提交前 / 待确认 | | confirmed / inferred / pending |

**本卡动作：**

- 至少走 1 条，最多保留 3 条核心流程
- 若页面存在页头主动作（如 `新增 / 创建 / 发布 / 导出`），至少保留 1 条对应流程
- 若页面存在行内主动作（如 `查看 / 编辑 / 详情 / 删除 / 启停`），至少保留 1 条对应流程
- 列表 / 管理页若两类都存在，两类都必须覆盖
- 先记录流程问题，再进入 checklist 收口
- 不能只写“流程存在问题”，必须指出卡在哪一步
- 低风险且可回收的创建动作，默认应走完整闭环；高风险动作才停下向用户确认

## 结构四问快扫卡（执行样式专项时先填）

| 项 | 判定 | 证据 | 结论 |
|----|------|------|------|
| 页头到首屏内容有没有接住 | pass / issue / pending / n/a | | |
| 主白底外边距稳不稳 | pass / issue / pending / n/a | | |
| 多列有没有收口 | pass / issue / pending / n/a | | |
| 有没有大块无效空白 | pass / issue / pending / n/a | | |

**本卡规则：**

- 主流程已完成或已明确停在提交前后，先填本卡，再决定是否进入样式细查
- 4 项必须逐项给结论，不能只写“整体偏松”或“版面还行”
- 若任一项命中 `issue`，相关问题必须升级到正式问题或 `style_review` 的明确维度结论，不能停留在总评
- 若 4 项都稳定，首轮不再做整页无差别样式深扫；只检查主流程经过区域和用户明确指出的区域
- 执行样式专项时必须记录 `style_review.trigger`；若用户明确要求、主流程区域可疑或用户框选区域触发细查，必须同时记录 `detail_check_required=true` 与 `detail_check_reason`

## 样式专项卡（命中后或用户明确要求时填写）

| 维度 | 判定 | 证据 | 结论 |
|------|------|------|------|
| 信息层级 | pass / issue / pending / n/a | | |
| 间距与对齐 | pass / issue / pending / n/a | | |
| 文字可读性 | pass / issue / pending / n/a | | |
| 色彩语义 | pass / issue / pending / n/a | | |
| 组件状态一致性 | pass / issue / pending / n/a | | |
| 密度与版面稳定性 | pass / issue / pending / n/a | | |

**本卡规则：**

- `url` / `screenshot` 默认执行；用户明确要看样式时，3 种模式都执行
- 只能在核心流程已完成或已明确停在提交前后填写，不能替代主流程走查
- 必须先完成「结构四问快扫卡」；只有结构命中、主流程区域可疑、或用户明确要看样式时，才展开本卡
- 进入本卡后，六个维度必须全部填写；不符合样式规范的观察必须进入正式 `issues[]`，不影响任务完成或理解效率时定为 `P3`
- `code` 模式只有在拿到明确样式证据时才写确定结论；否则优先 `pending`
- 本卡用于把样式观察收敛成 1 段 `style_review.summary` 和 1–3 条 `priority_actions`
- 不把纯主观审美偏好写成问题；必须写清“哪里、现象、为什么影响体验”
- 用户提供箭头 / 框选 / 补充截图指出样式区域时，应纳入优先细查范围
- `间距与对齐`、`密度与版面稳定性` 一旦命中 `issue`，不得让 `UX-1.2` 与 `UX-3.1` 同时保持 `pass`
